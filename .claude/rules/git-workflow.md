# Git workflow

## Перед работой
- Прочитай эти правила до Git-операций. Проверь status, текущую ветку и актуальность origin/main (fetch).
- main — стабильная ветка: разработка только в отдельной ветке от актуальной origin/main. Префиксы: feat/, fix/, refactor/, test/, docs/.
- При незакоммиченных изменениях не переключай ветку и не исправляй их автоматически: сначала установи происхождение; исключение согласуй с пользователем. Чужие изменения не перезаписывай.

## Проверки и коммиты
- Один коммит — законченная проверенная логическая задача; не откладывай независимые блоки до одного финального коммита и не создавай искусственные/пустые коммиты.
- Перед коммитом проверь `git diff`, `git diff --cached`, `git status`; добавляй файлы выборочно.
- Для функциональности: релевантные тесты, `npm run lint`, `npm run typecheck`, сборка при изменении приложения. Перед сдачей продуктового этапа — полный необходимый набор из CLAUDE.md. Для config/docs-only — профильные проверки конфигурации/ссылок/diff; продуктовые проверки не требуются без затрагивания приложения.
- Падения исследуй, не скрывай и не отключай проверки ради зелёного результата. Указывай существующие блокеры и пропущенные команды честно.
- Не включай секреты, .env, токены, пароли, локальные БД, временные файлы и чужие worktrees. Не выдавай незавершённую функцию за готовую.

## Публикация
- Commit/push/PR выполняй только при явном разрешении в текущей задаче. Тогда сохраняй проверенные логические блоки локально и регулярно отправляй рабочую ветку на origin; по завершении создай PR в main, если CLI/авторизация доступны. Иначе сообщи блокер и подготовь описание PR.
- PR содержит изменения, коммиты, проверки, миграции (или их отсутствие) и ограничения. Merge выполняет владелец продукта, не агент. Ветку после PR не удаляй без разрешения.
- Без отдельного разрешения запрещены force push (включая with-lease), reset --hard, git clean, удаление веток, переписывание опубликованной истории, разрешение конфликтов с потерей версии и миграции с потерей данных. При неожиданных конфликтах/проблемах истории остановись и сообщи.

## Отчёт
После каждого коммита: результат, hash, основные файлы, проверки. По завершении: ветка, список коммитов, PR (или блокер), реализованные сценарии, тесты и ограничения. Готовность продуктовой функции требует реального UI/API/PostgreSQL, а не намерения.

Историческое требование ветки feat/shift-applications относится только к этапу 2; не используй её для новых самостоятельных задач. Перед следующим продуктовым этапом сверь docs/PROJECT_CONTEXT.md и docs/FEATURE_MATRIX.md.
