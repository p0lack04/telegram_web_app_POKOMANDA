# Git Workflow — обязательные правила проекта

Эти правила обязательны для всех задач разработки в проекте «Команда».

## 1. Ветки

- `main` — основная стабильная ветка.
- Запрещено выполнять разработку непосредственно в `main`.
- Каждая самостоятельная задача или этап выполняется в отдельной ветке.
- Новые ветки создаются от актуальной `origin/main`.
- Имена веток: `feat/`, `fix/`, `refactor/`, `test/`, `docs/`.
- Перед началом работы проверь `git status`, текущую ветку и актуальность `origin/main`.
- Если рабочая директория содержит незакоммиченные изменения, не переключай ветки и не пытайся автоматически их исправлять. Сначала разберись с их происхождением.

## 2. Коммиты

Создавай коммиты по факту завершения логически самостоятельной работы.

Примеры:
- `feat: implement shift application API`
- `feat: add application management UI`
- `feat: implement position assignments`
- `fix: prevent duplicate shift applications`
- `test: cover application permission checks`
- `docs: update feature matrix`

Обязательные правила:
- Не откладывай все изменения до одного финального коммита.
- Один коммит должен отражать одну законченную логическую задачу.
- Перед коммитом проверь `git diff`, `git diff --cached` и `git status`.
- Добавляй файлы выборочно, а не бездумно через `git add .`.
- Не коммить незавершённый функционал под видом готового.
- Не создавай пустые или искусственные коммиты.
- Не включай секреты, `.env`, токены, пароли, локальные базы и временные файлы.
- Не переписывай историю опубликованных веток.

## 3. Проверки

Перед коммитом соответствующей функциональности:
- Запусти релевантные тесты.
- Проверь `npm run lint`.
- Проверь `npm run typecheck`.
- Проверь сборку, если изменения затрагивают приложение.
- Для завершённого этапа запусти полный набор проверок проекта.

Если тесты не проходят, сначала попробуй исправить причину. Не скрывай ошибки и не отключай проверки ради зелёного результата.

## 4. Push и Pull Request

- После проверенного логического блока сохраняй коммит локально.
- Отправляй рабочую ветку на `origin` регулярно, чтобы подтверждённая работа сохранялась на GitHub.
- После завершения этапа создай Pull Request в `main`.
- В PR укажи изменения, коммиты, тесты, миграции БД и оставшиеся ограничения.
- Не выполняй автоматический merge.
- Не удаляй ветку после PR без разрешения пользователя.

## 5. Запрещённые операции без разрешения пользователя

Не выполняй:
- `git push --force` и `git push --force-with-lease`;
- `git reset --hard`;
- `git clean`;
- удаление веток;
- переписывание опубликованной истории;
- автоматическое разрешение конфликтов с потерей одной из версий;
- merge в `main`;
- операции с миграциями, способные привести к потере данных.

При неожиданных конфликтах или проблемах с историей остановись и сообщи пользователю.

## 6. Отчётность

После каждого коммита сообщай:
- краткое описание результата;
- hash коммита;
- список основных изменённых файлов;
- выполненные проверки и их результат.

После завершения этапа сообщай:
- название ветки;
- список коммитов;
- ссылку на Pull Request;
- реализованные сценарии;
- результаты тестирования;
- известные проблемы и незавершённые функции.

## 7. Главное правило

Для этапа 2 обязательная ветка — `feat/shift-applications`, созданная от актуальной main. Разрешение на commit/push/PR дано в задаче этапа; merge выполняет пользователь. Перед следующим этапом сверить `docs/PROJECT_CONTEXT.md` и `docs/FEATURE_MATRIX.md`.

Коммит означает фактически выполненную и проверенную работу, а не намерение её выполнить.

Никогда не заявляй о готовности функции, если она не работает через реальный интерфейс, серверный API и PostgreSQL.
