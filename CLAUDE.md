# «Команда» — инструкции разработки

Telegram Mini App управления сменами педотряда. Стек: React 18 / TypeScript / Vite / TanStack Query; Fastify 5 / Zod / Prisma 6 / PostgreSQL; Vitest и Playwright. Сохраняй рабочие сценарии; демо не доказывает готовность production.

## Контекст и границы
- Начинай с `docs/PROJECT_CONTEXT.md` и `docs/FEATURE_MATRIX.md`; затем читай релевантные модули и разделы `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/PERMISSIONS.md`. Исторические отчёты — не текущая матрица готовности.
- `1.txt` — исходные требования, `2.txt` — расширение, `3.txt` — оригинальное демо. Сохраняй их неизменными, не добавляй обратно в Git. Для нового полного аудита или пересмотра продуктовой архитектуры/требований прочитай все три полностью; для ограниченной задачи используй нужные разделы и утверждённые ADR, не повторяя уже выполненное исследование. Если источников нет, сообщи, не подменяй их догадками.
- Конфликты требований сверяй с ADR; новое бизнес-правило, изменение данных/прав или неразрешённый конфликт согласуй с владельцем продукта. Не меняй roadmap самовольно.
- Один backend и один workspace lockfile; без второго сервера/state manager и big-bang rewrite. Слои UI → API → application services/domain policies → persistence/integrations. Входы валидируются Zod; ошибки единообразны; DTO — allowlist, пагинация и фильтры на сервере.

## Бизнес-инварианты
- User.role (`ADMIN/LEAD/TRAINEE`), onboarding, accountStatus, допуск на смену (APPROVED Application), ShiftRole и SquadMember — разные состояния. Одобрение не назначает должность; должность не меняет глобальную роль и не создаёт членство.
- Смена: четыре этапа; видимость `ADMIN_ONLY/ADMIN_LEAD/ADMIN_LEAD_TRAINEE` применяется сервером к спискам, деталям, поиску и связанным данным. Флаги набора независимы. Не вводи автоматические ограничения по этапу без согласования.
- Сначала active account и scope (видимость/принадлежность смене и объекту), затем permission и field-level policy. Единый `ROLE_PERMISSIONS`; неизвестная должность не даёт прав. Заместитель не назначает руководителя и не повышает глобальную роль.
- Squad принадлежит Shift; SquadMember — источник членства. CHILD без User, педсостав с User; связи одной смены валидируются. `view_own` ограничен конкретным отрядом, `view_all` — отдельное право.
- Комнаты/корпус/оплата/заезд — отдельные полевые права. PARTIAL требует непустого paymentNote; сумму/валюту не изобретай. Совпадающее ФИО — не идентификатор и не основание автоматического слияния.
- DailyMark: одна запись на SquadMember + календарную дату в timezone смены. SurveySubmission: одна атомарная уникальная запись user+survey; повторы запрещены, аудитория/обязательные вопросы проверяются сервером.
- TechRequest владеет единственным programItemId. Назначение исполнителя требует техлида и проверки должности исполнителя на той же смене. ProgramItem может ссылаться на BankEvent; изменения программы аудируются, автор/ответственный не обходит scope/полевые права.
- Несколько должностей допустимы; число завершённых смен считай по DISTINCT shiftId. Пересмотр закрытого решения/повторная заявка требуют отдельной политики; ручное добавление не обходит REJECTED.

## Безопасность и достоверность
- Telegram raw initData проверяется только сервером по официальному HMAC-алгоритму: подпись, auth_date/TTL, replay. initDataUnsafe/переданный user ID не доказывают identity. Сохраняй действующую opaque cookie/session стратегию; токены не в localStorage.
- Каждый защищённый endpoint проверяет auth, object-level и field-level доступ; UI не является защитой. Не ослабляй действующие проверки ради удобства.
- Минимизируй PII детей, ограничивай доступ и сроки хранения; медицинские сведения не предлагай собирать без отдельного обоснования и решения. Приватные комментарии кандидатов/стажёров недоступны стажёрам; каждый запрос проверяет полномочия и scope.
- Личные документы — чувствительные метаданные, не сканы без отдельного решения. Доступ ограничен и аудируется. Файлы банка — приватное хранилище и авторизованная выдача; сервер проверяет размер, расширение, MIME/содержимое, безопасное имя и сканирование где доступно. Не храни uploads в Git или публичных data URLs.
- Секреты только в server env с валидацией при старте; не во frontend/VITE_*, логах или Git. Не логируй токены, initData, телефоны, даты рождения, приватные комментарии и ссылки на документы.
- Связанные денежные/статусные операции, аудит и уведомления — транзакционно, с ограничениями БД и защитой повторов/конкуренции. Схема меняется только с новой миграцией и тестами; применённые миграции не редактируй, опасные изменения требуют backup/плана восстановления.
- CSV/XLSX/Google Sheets: parse/validate → preview/mapping/errors → подтверждение → запись; не перезаписывай по ФИО. Только реальные интеграции, не сгенерированные строки. Уведомление в inbox не означает доставку Telegram; delivery требует очереди/retry/idempotency. Dev/test seed — синтетический; не удаляй демо-сценарии до контролируемого seed.

## Работа и критерии завершения
- Перед крупными изменениями покажи краткий план и риски. Проверь исходный status и baseline релевантного scope; работай небольшими вертикальными срезами, добавляя regression/negative tests.
- После малого изменения запускай целевые проверки, не весь набор автоматически. Перед сдачей продуктового этапа: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; UI-потоки — `npm run test:browser`, БД — проверки миграций на PostgreSQL. Для config/docs-only — профильный валидатор и проверки ссылок/diff; пропуски объясни.
- Готовая функция — реальный UI → API → PostgreSQL, серверные проверки, тесты позитивных/негативных сценариев, loading/error/empty/success/permission-denied состояния и обновлённые инструкции. Mock/TODO/alert не считаются реализацией. Не заявляй проверку, которую не запускал; блокеры укажи явно.
- Mobile-first, спокойный рабочий интерфейс, без переименования терминов; светлая/тёмная темы, доступность и reduced motion. Подробности — профильный skill.
- Обновляй существующие постоянные документы и `docs/DEVELOPMENT_LOG.md` по изменившемуся scope, не создавай их копий и не меняй статусы функций при config-only работе.
- Отвечай по-русски: результат, файлы, выполненные команды/результаты, ограничения и следующие задачи. Показывай diff вместо больших копий кода.

## Git
Перед любой Git-операцией прочитай `.claude/rules/git-workflow.md`. Отдельная ветка от актуальной origin/main, не разработка в main; чужие незакоммиченные изменения сохраняй. Commit/push/PR — при разрешении пользователя, после проверок. Merge выполняет владелец продукта.

## Skills и модели: выбор по задаче, не обязательный fan-out
Загружай только относящийся к задаче skill из `.claude/skills/<name>/SKILL.md`:
- `backend-api` — API/services/DTO; `database-prisma` — schema/SQL/миграции.
- `rbac-security` — auth/RBAC/PII; `telegram-mini-app` — WebApp adapter/auth/navigation.
- `imports-files-integrations` — imports/storage/Google/Bot delivery.
- `ui-ux-redesign` — UX/доступность; `qa-testing` — тест-план/регрессии; `code-review` — ревью diff.
- `project-audit` — полный аудит по запросу или при неизвестной/существенно изменившейся структуре, не при каждом исправлении.

| Задача | Модель / исполнитель |
|---|---|
| Архитектура, сложные требования и технические решения | Opus, главная сессия |
| Основная реализация, backend/frontend, тесты, документация | Sonnet, `implementation` |
| Миграции, сложные SQL/Prisma | Sonnet с контролем Opus |
| Простой поиск файлов/мест реализации, read-only исследование | Haiku, `quick-scout` |
| Простая классификация и краткий отчёт | Haiku, `quick-scout` |
| Итоговый контроль сложной задачи | Opus, главная сессия |
| Безопасность/PII | Sonnet (`security-reviewer`) или Opus по риску |

Это рекомендации делегирования, не автоматический router: настройки не переключают главную сессию по типу задачи. Главная сессия — `opus`; agents задают `sonnet`/`haiku` frontmatter aliases. Не подставляй неизвестные provider model ID и не меняй env/секреты ради маршрутизации.

Opus выполняет малую задачу сам, если передача контекста дороже работы. Ограниченную реализацию делегируй Sonnet, простой самостоятельный поиск — Haiku, когда это уменьшает общую стоимость завершённой задачи. Не запускай агента на каждую мелочь, дублирующих агентов или параллельную работу, эффективно решаемую одной сессией. Для независимого security review дай diff и scope без навязывания вывода; Haiku не принимает архитектурных решений, не меняет permissions/схему БД и не проверяет критичную безопасность.

При делегировании передай цель, границы файлов, принятые решения, проверки и ожидаемый краткий результат; не проси пересказывать проект. Не перечитывай большие документы и не повторяй исследование без причины; используй найденные file:line и узкие excerpts. Безопасность и нужные инструменты/проверки не отключай ради экономии. Подробный аудит конфигурации и ограничения Tooken: `docs/CLAUDE_CODE_CONFIG.md` (читать при настройке, не в каждой задаче).
