# Педагогический отряд «Команда» — инструкции для Claude Code

## Миссия
Довести существующее демо Telegram Mini App «Команда» до надёжного, безопасного и удобного продукта. Сохраняй полезные сценарии и предметную область исходника, но не путай демонстрационную симуляцию с production-реализацией.

## Исходная точка и известные факты
- Исходный репозиторий: https://github.com/p0lack04/telegram_web_app_POKOMANDA
- На момент подготовки комплекта репозиторий содержит `3.txt` (около 435 КБ) и короткий `README.md`; это не полноценная структура приложения.
- `3.txt` — единый большой React-компонентный файл с CSS, UI, состоянием, seed-данными, бизнес-логикой и объектом `api`.
- В исходнике явно обозначено `REST API (симуляция)`: данные находятся в локальном in-memory store (`seedDb`, `store`, `useDb`), авторизация `api.auth.telegram` выбирает пользователя по ID из seed-данных и формирует имитационный токен. Это НЕ Telegram initData validation, НЕ серверная сессия и НЕ постоянная БД.
- Импорт Google Sheets в исходном коде частично имитируется: `parseGoogleSheet` создаёт демонстрационные строки, а не загружает фактическое содержимое таблицы.
- В интерфейсе документы представлены метаданными; в форме явно написано, что файлы не загружаются.
- Есть полезная предметная модель: роли ADMIN/LEAD/TRAINEE, этапы смены, должности и permissions, Squad/SquadMember, DailyMark, BankEventFile, ProgramItem, TechRequest, Survey/SurveyQuestion/SurveyAnswer, комментарии, документы, уведомления и журнал программы.
- Существующие экраны и обработчики являются источником требований, но не доказательством работоспособности интеграций.
- Дополнительная спецификация пользователя расширяет демо: полноценный backend, PostgreSQL/Prisma, безопасный Telegram auth, Excel/CSV import, хранилище файлов, onboarding/accountStatus, RBAC по должностям на смене, опросы, техзапросы, дневные отметки, комнаты/оплата/заезд и аудит изменений.

Если структура репозитория изменилась, сначала перепроверь её. Не считай приведённые выше наблюдения неизменными после новых коммитов.

## Обязательный рабочий процесс
1. **Инвентаризация**: изучи все файлы, package manifests, scripts, env examples, migrations, tests, workflows и историю текущих изменений. Не перезаписывай незакоммиченные пользовательские правки.
2. **Baseline**: запусти доступные install/lint/typecheck/test/build команды. Зафиксируй, что проходит и что падает до изменений.
3. **Карта функций**: сопоставь каждый экран/действие демо с реальной реализацией: UI-only, локальная симуляция, API-backed, persisted, tested.
4. **Архитектурное решение**: предложи целевую структуру и этапы миграции. Сохраняй рабочие сценарии; не делай big-bang rewrite без причины.
5. **Реализация**: небольшие вертикальные срезы UI → API → DB → auth/permissions → tests. Не оставляй фиктивных кнопок и заглушек под видом готовой функции.
6. **Проверка**: после каждого среза запускай релевантные тесты, typecheck, lint и build. Добавляй regression tests.
7. **Отчёт**: перечисли изменённые файлы, поведение, команды проверок и оставшиеся риски. Не заявляй о запуске команд, которые не запускал.

## Приоритеты продукта
P0 — безопасность и достоверность данных:
- Проверка Telegram `initData` только на сервере по официальному алгоритму Telegram; проверять `auth_date`, подпись, допустимый возраст данных, не доверять `initDataUnsafe` как доказательству личности.
- Никаких секретов бота, JWT secrets, DB credentials или service-account ключей во frontend.
- Серверная авторизация для каждого защищённого endpoint и каждой сущности; скрытие кнопок в UI не является контролем доступа.
- RBAC: глобальная роль пользователя отдельно от должности/permissions на конкретной смене. Все проверки делать на сервере и учитывать принадлежность к смене/отряду.
- Защита персональных данных, особенно несовершеннолетних: минимизация, ограничение доступа, безопасные логи, сроки хранения и отсутствие публичных ссылок на документы.
- Валидация файлов по размеру, MIME и расширению на сервере; приватное хранилище, авторизованная выдача, безопасные имена, антивирусная проверка/сканирование где доступно.
- Транзакции и ограничения БД для денежных/статусных/связочных операций.

P1 — функциональная целостность:
- PostgreSQL + Prisma (если текущий стек не диктует обоснованное иное).
- Реальная персистентность, миграции, индексы, уникальные ограничения и seed только для dev.
- Импорт CSV/XLSX с preview, mapping, валидацией строк, отчётом ошибок и подтверждением до записи.
- Реальная загрузка/скачивание BankEventFile.
- Реальные Google Sheets интеграции только через OAuth/API/публичный экспорт с явной обработкой доступа; не имитировать импорт.
- Уведомления через Telegram Bot API с очередью/retry/idempotency и graceful fallback.
- Опросы с серверным контролем аудитории и защитой от повторной отправки.
- Аудит критичных действий.

P2 — UX и визуальное качество:
- Mobile-first Telegram Mini App, safe areas, Telegram theme params, viewport, back button, MainButton при необходимости, haptics ненавязчиво.
- Чёткая навигация, компактная типографика, доступные контрасты, большие touch targets, skeleton/loading/error/empty states.
- Не перегружать главную; основные сценарии доступны за 1–2 действия.
- Поддерживать светлую/тёмную темы и системные настройки.
- Уважать `prefers-reduced-motion`; не использовать анимацию как замену обратной связи.

## Доменная модель и правила
- Глобальные роли: `ADMIN`, `LEAD`, `TRAINEE`. Не превращай должности смены в глобальные роли.
- Смена имеет 4 этапа: отбор педсостава, отбор стажёров, программа и роли, проведение смены.
- Видимость смены: `ADMIN_ONLY`, `ADMIN_LEAD`, `ADMIN_LEAD_TRAINEE`; сервер должен применять её ко всем спискам, деталям, поиску и связанным данным.
- Должности на смене дают permissions через единый каталог `ROLE_PERMISSIONS`; права должны быть описаны централизованно, проверяемы и тестируемы.
- Squad относится к Shift. SquadMember связывает участника с отрядом; не допускай дублирующих источников членства без чётких правил синхронизации.
- Участник отряда может быть User (ведущий/стажёр) или ребёнок без аккаунта. Модель должна различать эти случаи и валидировать обязательные поля.
- Комнаты, корпус, оплата и заезд должны редактироваться только соответствующими permissions. Для частичной оплаты нужна сумма/заметка согласно согласованному бизнес-правилу.
- DailyMark уникальна по согласованному ключу (например, participant + shift + date + markType); уточни, допустимы ли несколько отметок за день.
- ProgramItem может ссылаться на BankEvent. Изменение программы логируется; ответственный/автор не должен обходить права редактирования.
- TechRequest имеет статусный workflow, приоритет, назначенного исполнителя, автора, смену и необязательную связь с ProgramItem. Избегай дублирования `programItemId` в обеих сторонах связи без причины.
- Survey, SurveyQuestion, SurveyAnswer: типы TEXT/CHOICE/MULTIPLE_CHOICE/RATING/SCALE; аудитория проверяется сервером; уникальность ответа определяется бизнес-правилом (обычно один submission на пользователя и опрос, ответы по вопросам внутри submission).
- Onboarding и `accountStatus` — разные состояния. Не смешивай отправку анкеты, подтверждение профиля и допуск к конкретной смене.
- Документы ведущих — чувствительные метаданные/файлы. Доступ ограничен и журналируется.
- Комментарии о стажёрах/кандидатах — приватные; сервер проверяет право чтения/создания на каждом запросе.
- Google Sheets/Excel import не должен автоматически доверять входным значениям или перезаписывать данные без preview и подтверждения.

## Архитектурные правила
- Сначала выясни фактический стек. Не добавляй второй backend или state manager, если существующий стек подходит.
- Если backend отсутствует, спроектируй API как отдельный слой; предпочтительный baseline — TypeScript + Node.js (Express/Fastify/Nest по контексту), Prisma и PostgreSQL.
- Разделяй UI, application services, domain rules, persistence и integrations.
- Используй схемы валидации на границе API (Zod или существующий эквивалент).
- Единый формат ошибок; корректные HTTP-коды; пагинация/фильтры на сервере.
- Никаких бизнес-правил только в React-компонентах.
- Не храни access token в localStorage без обоснования; предпочитай безопасную cookie/session стратегию, совместимую с Telegram Mini App и инфраструктурой.
- Конфигурация через env, валидируется при старте; `.env` не коммитить.
- Миграции должны быть обратимы насколько возможно; опасные миграции описывать отдельно.
- Не логировать initData, токены, телефоны, даты рождения, содержимое приватных комментариев и ссылки на документы.

## UI/UX направление
Визуально — современный, спокойный, дружелюбный рабочий инструмент для педотряда, не «админка из таблиц» и не игровой интерфейс для детей. Используй ясную иерархию, нейтральную поверхность, один выразительный акцент, семантические статусы и аккуратные карточки. Не меняй смысл терминов без согласования.
- Главная: приветствие, текущая смена/следующий шаг, персональные задачи и компактные быстрые действия.
- Смены: карточки с датами, этапом и доступностью; подробная страница с понятными вкладками.
- Мой отряд: состав, роли, отметки, расселение/оплата/заезд — по правам пользователя.
- Программа: календарная/дневная группировка, фильтры, ответственный, место/время, связь с мероприятием банка.
- Банк мероприятий: поиск, категории, возраст, длительность, материалы/файлы и действие «добавить в программу».
- Опросы: статус/срок/аудитория, прогресс заполнения, доступные результаты по правам.
- Профиль: onboarding, подтверждение анкеты, документы и статусы — без раскрытия лишних персональных данных.
- Все экраны: loading, empty, error, success, disabled, permission-denied states.

## Definition of Done
Функция считается завершённой только если:
- есть реальный пользовательский сценарий, а не только кнопка/макет;
- данные сохраняются и читаются через предусмотренный backend;
- сервер валидирует вход и права;
- есть тесты ключевых правил и негативных сценариев;
- есть loading/error/empty/success states;
- нет секретов и утечек приватных данных;
- типизация, lint и build проходят (или задокументированы существующие блокеры);
- инструкции запуска/конфигурации обновлены.
