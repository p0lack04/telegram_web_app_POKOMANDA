# Права: staffing, Squad и дети

## Программа (этап 4, 2026-11-15)

`ProgramWorkflowService`: active account → видимость смены → доступ к программе (ADMIN, должность с `program.view` либо APPROVED-допуск) → действие/поля. Неизвестная должность не даёт полномочий. Одобрение даёт участнику просмотр, но не полномочия редактирования.

- `program.edit`: создание и управление любым пунктом, типом, ответственным, порядком, удалением и блокировкой.
- `program.edit_entertainment`: создание/управление только ENTERTAINMENT; смена типа, порядка и блокировки запрещена.
- Ответственный своего пункта: название, описание, локация, время, связь с доступным банком. Дата, тип, ответственный, порядок и удаление требуют полномочий редактора.
- Заблокированный пункт требует явной разблокировки полномочным редактором. Устаревший `updatedAt` в PATCH/DELETE/lock/reorder даёт 409; связанные изменения и аудит транзакционны.
- Ответственный выбирается только из CONFIRMED/onboarded пользователей с APPROVED-допуском той же смены. Идентификатор из клиента повторно проверяется сервером.
- Предложения создают LEAD с APPROVED-допуском и ADMIN. Автор видит свои предложения, ADMIN — все предложения смены и принимает решение PENDING→ACCEPTED/REJECTED. Решение не редактирует программу автоматически.
- История действий доступна в scope программы; в ответе нет текстов предложений, закрытого банка, контактов и содержимого приватных комментариев.
- Ссылка программы на закрытый банк скрыта, если пользователь не автор материала и не ADMIN. Доступ к программе не даёт доступ к файлам банка; файл-сервисы ещё не реализованы.

Чтение: `GET /shifts/:id/program?date=YYYY-MM-DD` (по дням), `/program-candidates?search=&page=&pageSize=`, `/program-history?page=&pageSize=`, `/program-proposals?page=&pageSize=`. Изменения: POST/PATCH/DELETE `/program`, PATCH `/program/:itemId/lock`, PATCH `/program/reorder`, POST `/program-proposals`, PATCH `/program-proposals/:proposalId`. У PATCH/DELETE существующего пункта обязателен текущий `updatedAt`; у reorder снимок передаётся для каждого пункта.

## Дети и импорт

`participants.import` разрешает загрузку и создание preview в видимой смене и доступных отрядах. `participants.edit_room` разрешает ручное изменение `squadId/building/room`; обновление существующих строк XLSX требует обоих разрешений. Ручное создание CHILD требует `squad.manage`. ФИО, дата рождения, `memberType` и `userId` после создания не изменяются. Сначала проверяются active account, видимость смены и object scope, затем permission.

Список детей возвращает `capabilities: {create, editPlacement, import}` для текущего пользователя. `create` дополнительно учитывает management scope: `view_all` не расширяет локальное управление. UI скрывает недоступные действия, а каждый mutation повторно проверяет серверные права. Перевод выбирается из доступных отрядов этой смены; сервер проверяет обе стороны перевода.

## Squad read-only (этап 3, D1/D2/D3/D14/D12 APPROVED — 2026-11-13)

Порядок проверок: active account → visibility смены → итоговый permission set → object scope. `squad.view_all` разрешает все отряды конкретной доступной смены. Иначе `squad.view_own` разрешает только отряды со связью через `ShiftRole.squadId` либо `SquadMember.userId` при совпадении user/shift/squad. Источники объединяются; null squadId не является связью. Membership само по себе permissions не создаёт. Несколько членств одной смены допустимы, но не повышают права до `view_all`. `squad.manage` не заменяет права просмотра.

| Endpoint / условие | Результат |
|---|---|
| List + view_all | Все отряды конкретной доступной смены |
| List + только view_own | Только связанные отряды; фильтрация в БД до пагинации/count |
| List видимой смены без view permissions | 403, даже при наличии membership |
| Detail | Тот же object scope, что у list |
| Несуществующий/чужой/недоступный squad или неверная пара shift+squad | 404 без раскрытия существования |
| Невидимая/несуществующая смена | 404 |
| Нет auth / inactive account | Существующие 401 / 403 ACCOUNT_NOT_READY |

DTO отряда — только `id/name/color/sortOrder`. Без количества участников, состава, CRUD, DailyMark и персональных полей. `ROLE_PERMISSIONS` и staffing не меняются. Staffing metadata сохраняет существующий id/name список для менеджеров должностей.

## Staffing

Базовый каталог — `backend/src/domain/permissions.ts`, authentication — существующий AuthService. Новый модуль обязан сначала проверить active account и видимость смены, затем действие и target scope.

| Действие | Доступ |
|---|---|
| Видимые смены | CONFIRMED + onboarded, фильтр visibility |
| Подать заявку | собственная identity; LEAD→LEAD_RECRUIT, TRAINEE→TRAINEE_RECRUIT; соответствующий набор открыт |
| Мои заявки/назначения/история | только собственные записи и видимые смены |
| Все заявки смены / решение / ручное добавление | ADMIN |
| Открыть/закрыть набор, сменить этап | ADMIN |
| Минимальный принятый персонал | ADMIN или shift.manage_roles в данной видимой смене |
| Назначить/снять должность | ADMIN или shift.manage_roles; target принят и active |
| Назначить/снять «Руководитель» | только ADMIN, также на сервере |
| Привязать должность к отряду | дополнительно тот же shift + target состоит в squad |
| История всей смены | ADMIN / shift.manage_roles, без чужих анкетных решений у не-ADMIN |
| Уведомления | только собственный inbox |

API не меняет User.role, accountStatus или чужой userId через подачу заявки. Минимальный DTO сотрудника содержит ID, ФИО, глобальную роль; не включает телефон, Telegram ID, дату рождения, документы или приватные комментарии. Отдельные решения не отменяют ранее выданные назначения — пересмотр закрытой заявки не реализуется в этом этапе.

## Stage 3Б: отвязка должности

Отвязка доступна только активному пользователю с `shift.manage_roles`; назначение «Руководитель» по-прежнему изменяет только ADMIN. Сервер проверяет видимость смены, объект и известность должности. После отвязки права по position сохраняются, но squad scope больше не предоставляется этой связью. Перевод/снятие членства блокируется с 409, если это разрушит последнюю связь.
