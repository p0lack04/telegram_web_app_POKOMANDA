# Первичный обзор репозитория

Дата обзора: 2026-11-11  
Репозиторий: https://github.com/p0lack04/telegram_web_app_POKOMANDA  
Ветка по умолчанию: `main`

## Что доступно
В корне репозитория на момент просмотра:
- `3.txt` — 435 503 байта, основной исходник демо.
- `README.md` — 28 байт.
- Отдельных `package.json`, backend, Prisma schema, migrations, tests и deployment config в дереве репозитория не обнаружено.

## Наблюдения по `3.txt`
- Один большой React-файл, React hooks, JSX и встроенный CSS.
- В коде есть seed-функция `seedDb()`, in-memory `store`, `useSyncExternalStore` и `resetDb()`.
- Блок явно назван `REST API (симуляция)`.
- `api.auth.telegram(userId)` получает пользователя по переданному ID из локального seed store и генерирует имитационный токен. Это не безопасная Telegram авторизация.
- `parseGoogleSheet()` проверяет строку/ID, но формирует примерные строки расписания локально; фактического чтения Google Sheets не делает.
- В форме документа указано «Только метаданные — файлы не загружаются».
- UI и доменная логика содержат полезные сценарии: смены и 4 этапа, visibility, должности/permissions, заявки, отряды, участники, оплата/заезд/комнаты, отметки по дням, банк мероприятий и файлы как модель, программа, техзапросы, опросы, документы, комментарии, уведомления, журнал изменений.
- Из-за единого файла и отсутствия проектной обвязки запуск/сборка не подтверждены.

## Главные выводы
1. Это богатый интерактивный прототип, но не подтверждённое production-приложение.
2. Первым этапом должен быть перенос в нормальную структуру проекта с воспроизводимой сборкой, тестами и документированными dev fixtures.
3. Параллельно требуется спроектировать backend, БД, Telegram auth и серверный RBAC. Нельзя просто «подключить PostgreSQL» к существующему mock API без доменного слоя и контрактов.
4. Необходимо сохранить демо-режим для UX разработки, но жёстко отделить его от production.
5. Поскольку в исходнике могут присутствовать демонстрационные персональные данные, их нельзя переносить в production seed или использовать как реальные данные.

## Решения, которые нужно принять до миграции схемы
- Как именно связаны `ShiftRole` и `SquadMember`: членство в отряде, должность и привязка к конкретной смене должны иметь однозначный источник истины.
- Может ли один участник состоять в нескольких отрядах одной смены и иметь несколько должностей?
- Для `CHILD` без User: какие поля обязательны, кто является ответственным за запись и как обеспечивается защита данных несовершеннолетних?
- `payment=PARTIAL`: нужна ли сумма, дата, комментарий, подтверждающий пользователь?
- `DailyMark`: допустимо ли несколько типов отметок за один день и кто может их менять?
- `Survey`: один ответ на опрос или повторное прохождение; требуется ли отдельная сущность submission?
- `TechRequest` ↔ `ProgramItem`: какой FK владеет связью, чтобы не дублировать её с двух сторон?
- `accountStatus` и `isOnboarded`: какие переходы допустимы и кто подтверждает профиль?
- Хранилище файлов: локальное для dev или S3-compatible для production; требования к хранению/удалению документов.
- Google Sheets: OAuth пользователя, service account или импорт CSV; кто выдаёт доступ?
- Возрастные ограничения регистрации и согласия: отдельно проверить юридические требования целевой юрисдикции и политику организации.

## Следующий технический порядок
1. Создать package manifest, React/TypeScript app entrypoint и воспроизводимый build.
2. Разбить исходник на компоненты, страницы, доменные типы, fixtures и адаптер API без изменения поведения.
3. Добавить тесты на текущие бизнес-правила и permission resolver.
4. Спроектировать Prisma schema и API contracts; согласовать неоднозначности выше.
5. Реализовать Telegram initData validation на сервере и безопасную сессию.
6. Перенести use cases по одному вертикальному срезу: shifts → squads/members → program/bank/files → surveys/tech → documents/notifications.
7. Провести security review, e2e и staging deployment.
