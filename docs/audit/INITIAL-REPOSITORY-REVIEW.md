# Аудит проекта — 2026-11-15

## Вывод
Проект уже не демо: работает единый React/TypeScript frontend → Fastify/Zod → PostgreSQL/Prisma. Реализованы безопасный вход, онбординг, подтверждение аккаунтов, смены, заявки, допуск, должности, история и внутренние уведомления. У этапа 3 есть backend и UI детей/XLSX, однако пользовательский цикл не завершён. Большинство остальных экранов из демо пока представлены лишь схемой БД.

Этот документ заменяет первичный обзор 2026-11-11 как актуальный аудит. История начала проекта остаётся в BASELINE.md и DEVELOPMENT_LOG.md. Приложение не изменялось в ходе аудита; перечисленные дефекты ещё не исправлены. Проверка выполнена основной сессией, без независимого security review.

## Источники и метод
Полностью прочитаны локальные 1.txt (первоначальные требования), 2.txt (расширенные требования), 3.txt (React-демо). Файлы не изменены и остаются вне Git. Требования сопоставлены с утверждёнными ADR-001–006, текущими routes/services/policies, frontend, Prisma schema/migrations и тестами. Graphify использован для навигации, выводы проверены по исходникам; граф не является доказательством готовности и частично разбирает Staffing.tsx.

1.txt задаёт смены/этапы/видимость, профили, роли, программу, банк, документы, комментарии, бота и интеграции. 2.txt добавляет должности и права смены, отряды/детей, оплату/заезд/размещение, ежедневные отметки, импорт, файлы, техзапросы и опросы. 3.txt — каталог пользовательских сценариев: in-memory store, fake JWT, delay, client-only permissions, generated Google rows, object/data URLs, симуляция бота и перезапись ответов опроса не переносимы как production-реализация.

При конфликте демо с ADR сохраняются ADR: отдельные admission/position/membership, CHILD без User, PARTIAL с примечанием, DailyMark member+date, уникальная атомарная SurveySubmission, единственный FK TechRequest.programItemId, метаданные личных документов без сканов. Новые правила не утверждены этим аудитом.

## Что уже сделано правильно
Auth/session не основаны на initDataUnsafe или клиентском user ID. Сервер повторно проверяет активность/видимость, неизвестные должности не выдают права, in-app уведомления повторно проверяют scope. Staffing сериализует изменения по Shift и использует version-CAS; audit/inbox сохраняются транзакционно. Состав отряда проверяется через серверные связи. CHILD импорт ограничивает ZIP/XLSX, проверяет CRC/размеры/XML, имеет ownership, TTL, mapping, snapshot, explicit commit и повторобезопасность. Схема обеспечивает identity/PARTIAL/date/unique/cross-shift ограничения; существующие миграции не требуется переписывать.
