## Этап 3. Отряды и участники

### 3А. Дети и XLSX — реализован и принят

Выполнены исправления A1–A4 и A6–A8 аудита:

- Создание ребёнка без отчества, размещение и перевод в доступный отряд той же смены.
- Полный preview XLSX: строки, кандидаты, значения до и после изменений, ошибки и пропуски.
- Явное сопоставление неоднозначных записей и подтверждение записи; повторный commit без дублей.
- Результат импорта, обновление списков детей, серверные capabilities и allowlist Shift DTO.
- Явная ошибка для неподдерживаемого типа участника в смешанном XLSX.

Неоднозначность в API обозначается `UNRESOLVED` и требует выбора пользователя. Редактирование identity, оплата и создание отрядов внутри импорта в этот срез не входят.

Приёмка 3А зафиксирована в журнале: UI → API → PostgreSQL, негативные проверки доступа, TTL/revision, повторный commit, mobile/light/dark/error/retry.

### 3Б. Отряды и членство педсостава — текущая реализация, приёмка открыта

В рабочей ветке реализованы формы создания/редактирования/удаления пустого отряда, поиск принятого активного сотрудника, добавление, перевод и подтверждённое снятие членства. Отдельно отображаются несколько доступных членств и должности; конфликт связанной должности ведёт к существующей явной отвязке. Серверные capabilities управляют UI; все операции повторяют scope и permissions на сервере. История действий сохраняется после снятия членства, не раскрывает персональные поля.

Проверяются no-op, повторное добавление, cross-shift, inactive/no admission, локальное управление при view_all, отрицательные роли, конкуренция, аудит и полный browser workflow. Итоговые результаты и текущая точка продолжения — в DEVELOPMENT_LOG.md. Архивирование заполненного отряда и снятие членства с зависимыми DailyMark остаются BLOCKED до отдельной политики; действующие FK-запреты сохранены.

### 3В. Оплата, заезд и ежедневные отметки — текущая реализация, приёмка открыта

Добавлены явные формы оплаты UNPAID/PARTIAL/PAID с обязательным примечанием PARTIAL и заезда boolean для детей и педсостава. Сохраняется двойная проверка squad.manage + соответствующее полевое право, а также scope участника. UI отправляет updatedAt; устаревший снимок возвращает 409, введённые значения остаются до явного перечитывания. Совместимые вызовы без снимка сериализуются блокировкой смены. No-op не создаёт повторный аудит.

DailyMark: список с пагинацией, выбор календарной даты, lookup конкретного дня, создание/изменение, CAS и атомарный аудит. В существующей модели уже хранится Shift.timeZone; сервер возвращает today в этом часовом поясе. Браузер не определяет дату неявно. Дата хранится SQL DATE с unique(member,date); операция удаления не вводится. Диапазон разрешённых дней не сужается новым правилом. Отдельно проверяются границы суток/года, високосный день, конкурентные действия и rollback.

## Этап 4. Программа, банк и файлы — частично реализован

### Что реализовано

- Серверный каталог банка: поиск, фильтры, пагинация, карточка, создание и редактирование.
- Базовый CRUD программы в API/PostgreSQL и привязка к публичному мероприятию банка.
- Аудит базовых мутаций и UI вкладки «Банк».
- CRUD программы через UI → API → PostgreSQL, выбор принятого активного ответственного той же смены с поиском и пагинацией, копирование содержимого из банка, отвязка и открытие доступного оригинала. Изменение копии не меняет оригинал.
- Просмотр программы по дням в экране смены, предупреждения пересечений времени, перестановка в пределах дня кнопками «Выше»/«Ниже». Пересечения не блокируют сохранение; для перестановки проверяются `program.edit`, `isLocked` и снимок `updatedAt`, ошибки откатывают всю транзакцию.
- Полевые права полного редактора, досугового блока и ответственного своего мероприятия. Управление блокировкой для `program.edit`, повторная проверка scope в транзакции, защита CRUD и перестановки от устаревшего снимка.
- История действий программы с автором/временем, серверным scope и пагинацией. Полные снимки значений до/после не сохраняются: аудит изменений содержит имена полей.
- Текстовые предложения ведущих с APPROVED-допуском на смену, собственный список и решения ADMIN (`PENDING → ACCEPTED/REJECTED`), пагинация и транзакционный аудит. Решение не меняет программу автоматически и не означает Telegram-доставку.

Программа подключена в экран смены. Закрытый оригинал банка и его ID не выдаются пользователю без доступа. Этап остаётся частичным из-за файлового блока.

### Что согласовано владельцем продукта

- Приватное S3-совместимое хранилище и обязательная проверка ClamAV до скачивания.
- Явное удаление файлов и очистка осиротевших объектов; автоматический срок удаления материалов не вводится.
- Пересечения времени вызывают предупреждение и не запрещают сохранение.
- Блокировкой управляют ADMIN, руководитель, заместитель и ответственный за программу.
- Ответственный редактирует содержание своего пункта; тип, ответственного, удаление и порядок меняют только уполномоченные должности.

Это утверждённые требования к дальнейшей реализации, а не список готовых функций.

### Текущая работа и условия закрытия

Файловые backend/UI реализованы в рабочей ветке: multipart upload, MIME/signature/size validation, random storage key, S3, ClamAV INSTREAM, PENDING/CLEAN/INFECTED/ERROR, запрет скачивания до CLEAN, повторная авторизация download, explicit delete, tombstone и orphan cleanup. UI включает progress, категории документов/медиа, безопасное preview и подтверждение удаления. Миграция аддитивна, без TTL материалов.

Обычные тесты используют реальные API/PostgreSQL и тестовые storage/scanner. Подготовлены изолированный compose, opt-in real-service тест и отдельный CI job. **BLOCKED локально:** Docker/S3/ClamAV недоступны; реальная приёмка не засчитана. До закрытия нужны успешные реальные CLEAN/EICAR/50 МиБ/private bucket/download/delete/cleanup проверки и итоговый browser smoke. Результаты публикуются в журнале, а не выводятся из наличия кода.

Уведомления программы/предложений остаются этапом 7. Merge и production deployment выполняются владельцем отдельно.

## Этап 5. Техзапросы и опросы — запланирован

Последовательность: техзапросы → опросы.

Техзапросы: создание, статусы, назначение исполнителя техлидом после проверки должности на той же смене. Единственный FK связи с программой принадлежит `TechRequest.programItemId`.

Опросы: конструктор, активация и аудитория, атомарная отправка, результаты, диаграммы и CSV. Одна запись `SurveySubmission` на user + survey; обязательные вопросы, типы и аудитория проверяются сервером.

Приёмка: запрет назначения постороннего и обхода scope автором, защита повторных/параллельных ответов, ограничение результатов по правам, защита CSV от formula injection и отдельные браузерные сценарии обоих модулей.

## Этап 6. Команда, документы, комментарии и знания — запланирован

Последовательность: каталог команды и чужой профиль с минимальными DTO → ADMIN изменение глобальной роли → статистика DISTINCT завершённых shiftId → приватные комментарии → документы → база знаний. Knowledge можно выполнить отдельным срезом после каталога банка без смешения сущностей.

До реализации согласовать видимость профилей/истории, сроки хранения ПДн и права документов. Документы содержат метаданные и сроки действия, без сканов. Глобальная роль не смешивается с должностью смены; ручной стаж не выдаётся за вычисленную историю.

Приёмка: стажёр не получает приватные комментарии списком или по direct ID, доступ к документам ограничен и аудируется, сроки проверяются, роль меняется только уполномоченным серверным сценарием. Обязательны негативные тесты DTO и scope.

## Этап 7. Реальные интеграции и уведомления — запланирован

Последовательность: CSV/расширенный импорт → Google Sheets и импорт/экспорт программы → персональные настройки уведомлений → outbox worker → bot webhook/commands → напоминания 30/14/7 → WebSocket, если подтверждён приоритет.

До Google выбрать OAuth/service account/допустимый экспорт; требование Google Docs уточнить отдельно. До доставки Telegram согласовать opt-in и события. Генерируемые строки не считаются интеграцией, запись в inbox не считается доставкой Telegram.

Приёмка: parse/validate → preview/mapping → explicit confirm без перезаписи по ФИО; реальные сбои и повторы; очередь с retry/backoff/idempotency; транзакционная запись outbox, мутации и аудита. Webhook проверяет секрет, команды и WebSocket соблюдают scope, доставка учитывает opt-out и активность получателя.

## Эксплуатация и условия релиза

Сквозная работа: безопасный ADMIN bootstrap, чистые env/examples, CI и актуальные инструкции. До пилота необходимы staging с HTTPS/same-origin/CSP, постоянная PostgreSQL, безопасные логи/метрики/readiness, очистка Session/TelegramReplay/preview, backup и проверенное восстановление, миграционный runbook. Для файлов нужны приватные S3 и ClamAV; отдельно требуются нагрузочная проверка импорта и реальный Telegram на мобильных устройствах.

Каждый срез включает loading/error/empty/success/permission-denied, mobile/light/dark/reduced-motion, Zod, объектные и полевые политики, транзакции/аудит и обновление постоянной документации.

Перед сдачей продуктового этапа: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; для UI — `npm run test:browser`, для изменений БД — проверки миграций на PostgreSQL. Пропуски и блокеры указываются явно.

Релиз требует закрытия применимых P0/P1, ролевой e2e-матрицы, проверки production Telegram, восстановления БД и мониторинга. Границы пилота с незавершёнными модулями определяет владелец продукта.
