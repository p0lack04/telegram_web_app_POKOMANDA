## Сначала — закончить текущий этап 3

### 3А. Дети и XLSX: исправления и приёмка — реализовано, 2026-11-15
Scope: A1–A4, A6–A8 аудита. Нормализация необязательного отчества; точные validation/permission ошибки; полная таблица preview с before/after и кандидатами; вывод результата/пропусков; query invalidation; UI перевода в доступный отряд; capabilities для кнопок; Shift DTO allowlist; проверка неподдерживаемого смешанного XLSX.

Приёмка: создать ребёнка без отчества, разместить и перевести в той же смене; показать NEW/UPDATE/UNCHANGED/AMBIGUOUS/ERROR/FORBIDDEN; повторить commit без дублей; обработать TTL/revision/изменённую запись/отозванное право; после импорта списки соответствуют БД. Browser-тест с настоящим API/PostgreSQL, негативные IDOR/field-level проверки и mobile/light/dark/error/retry. Не вводить редактирование identity, оплату или создание отрядов внутри импорта.

Результат: исправлены A1–A4, A6–A8. Форма допускает отсутствие отчества; UI показывает серверные ошибки и capabilities, перевод между доступными отрядами, все строки XLSX, кандидатов с ID/датой/размещением, before/after, пропуски и результат. Изменения обновляют списки детей всей смены. Сервер отдаёт allowlist Shift DTO и отклоняет строки смешанного XLSX с неподдерживаемым типом. Неоднозначность в действующем API обозначается UNRESOLVED; UI требует явного сопоставления. Проверки и ограничения фиксируются в [журнале](DEVELOPMENT_LOG.md).

Этап 3А завершён ранее. Этапы 3Б и 3В реализованы в текущем срезе; A5 сохраняется как отдельный незакрытый scope. Это фиксация выполненного scope, без изменения порядка этапов и бизнес-правил.

### 3Б. Отряды и членство педагогического состава — реализовано
Scope: создание/редактирование отряда, список педсостава, добавление принятого сотрудника в отряд, перевод/снятие членства отдельными действиями. Сначала согласовать удаление/архивирование, историю и последствия для связанных должностей; несколько членств уже допустимы. Одобрение заявки не создаёт членство, назначение должности не меняет глобальную роль.

Приёмка: ADMIN создаёт смену и отряды с нуля, принимает сотрудника, отдельно добавляет в состав и назначает должность. Проверить view_own/view_all, несколько членств, снятие доступа, cross-shift, неактивного/непринятого сотрудника, concurrency и audit. Любая схема меняется новой миграцией с PostgreSQL upgrade tests.

### 3В. Оплата, заезд и ежедневные отметки — реализовано
Scope: отдельные разрешения полей, PARTIAL с непустым примечанием без изобретённых сумм/валют, check-in, DailyMark на member+календарную дату timezone смены, собственные отметки стажёра. Уточнить политику исправления/снятия отметок.

Приёмка: нельзя менять поле с одним лишь доступом к карточке; forbidden поля не попадают в DTO; отсутствие дублей member+date, тесты границы суток/часового пояса и параллельных записей, атомарный audit, e2e уполномоченного и ограниченного пользователя.

## Этап 4 — программа, банк и файлы — частично реализовано (2026-11-15)
Последовательные срезы: банк metadata/catalog/search → private files upload/download/delete → программа смены и добавление из банка → reorder/conflicts/ответственный → предложения/решения/история. Knowledge можно выполнить отдельным небольшим срезом после каталога, без смешения сущностей.

До файлов выбрать storage, scanning и retention; до программы определить правила конфликтов/блокировок и изменений автором. Сохранять ProgramItem.bankEventId, scope смены и права на поля. Доступ к программе не должен раскрывать закрытый файл банка.

Приёмка: реальное приватное хранилище, проверка расширения/MIME/содержимого/лимитов 20/50 MB, авторизованная выдача; никакого публичного data URL. Программа сохраняется в PostgreSQL, порядок устойчив при конкуренции, изменения аудируются; search/filter/page серверные. Негативные IDOR и browser-потоки каждого среза.

Реализован первый вертикальный срез: серверный каталог банка мероприятий (поиск, фильтры, пагинация, карточка, создание и редактирование с авторизацией), программа смены (просмотр, создание, редактирование, удаление, привязка к публичному мероприятию банка), аудит мутаций и UI вкладки «Банк». ## Этап 5 — техзапросы и опросы
Сначала техзапрос: создание, статусы, назначение техлидом исполнителя с должностью той же смены, связь с ProgramItem через единственный FK. Затем опрос: конструктор, activation/audience, атомарная отправка, результаты/диаграммы/CSV.

Приёмка: нельзя назначить постороннего/неуполномоченного, автор не обходит scope; один SurveySubmission user+survey даже при параллельной отправке, сервер проверяет вопросы/типы/обязательность/аудиторию, CSV защищён от formula injection, результаты видны только уполномоченным. Отдельная browser-приёмка обоих модулей.

## Этап 6 — команда, документы, комментарии и знания
Срезы: каталог/чужой профиль с минимальными DTO → ADMIN изменение глобальной роли и статистика DISTINCT завершённых shiftId → закрытые trainee/selection comments → документы metadata/expiry/summary → knowledge CRUD/search, если ещё не сделан. Повышение роли не смешивать с должностью смены; manual experience не выдавать за вычисленную историю.

До реализации согласовать видимость профилей/истории, retention PII и права документов. Приёмка: стажёр не получает приватные комментарии ни списком, ни direct ID; документы без сканов, доступ ограничен и аудируется; истечение дат проверяется; роль меняется только уполномоченным серверным сценарием; негативные тесты всех DTO/scope.

## Этап 7 — реальные интеграции и уведомления
Срезы: CSV и согласованный расширенный import → Google Sheets (и требуемый программный import/export) → персональные notification preferences → outbox worker/retry/idempotency → bot webhook/commands → reminders 30/14/7 → WebSocket с фильтрованными подписками, если подтверждён приоритет.

До Google выбрать OAuth/service account/допустимый экспорт; требование Google Docs уточнить отдельно. Никаких генерируемых строк вместо интеграции. До bot delivery согласовать opt-in и доступные события. Outbox, mutation и audit сохраняются транзакционно.

Приёмка: parse/validate → preview/mapping → explicit confirm без перезаписи по ФИО; реальные сбои внешнего сервиса и повторы; worker не дублирует доставку, соблюдает opt-out/активность/scope; inbox не считается доставкой Telegram. Webhook проверяет секрет, команды не раскрывают чужие данные; reconnect WebSocket не расширяет доступ.
