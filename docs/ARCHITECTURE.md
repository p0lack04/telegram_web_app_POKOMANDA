# Архитектурные решения и этапы

Дата: 2026-11-11. Source of truth: полностью прочитанные 1.txt, 2.txt, 3.txt и CLAUDE.md. Исходный прототип сохраняется как неизменный источник сценариев, а не включается в production bundle.

## ADR-001 — постепенные вертикальные срезы
Используем существующее направление Fastify + TypeScript / React 18 + Vite + TanStack Query / Prisma + PostgreSQL, не создаём второй сервер. Рабочий tree не содержит remote-каркас; переносим необходимые идеи и доменные имена, но не заведомо сломанные entrypoints/фиктивные endpoints. Workspace backend/frontend, один lockfile. Слои routes → services/policies → Prisma. Общая runtime-валидация Zod на границе; DTO allowlists, единый error envelope. Неисполненные сценарии остаются в feature matrix, а не в виде фиктивных кнопок.

## ADR-002 — identity и сессии
Raw Telegram initData → HMAC SHA256 (ключ WebAppData), timingSafeEqual, строгие обязательные поля, TTL 5 минут, будущее не допускается, дублирующиеся ключи не допускаются. Одноразовый digest initData хранится транзакционно с созданием opaque session. Cookie HttpOnly, SameSite=Strict, Secure в production, same-origin deployment; unsafe API требует точный Origin. Token только в cookie, в БД SHA256 hash. TTL 12 часов. Каждый запрос перечитывает User (роль/статус не замораживаются в токене). Pending/rejected допускаются только к собственному статусу/онбордингу/logout, не к доменным данным. Нет dev-login по ID. Реальный Telegram нужен для интерактивного входа.

## ADR-003 — конфликты требований / безопасные допущения
- 1.txt запрещает файлы документов пользователя; 2.txt добавляет файлы БАНКА, не отменяя запрет на сканы личных документов. Личные документы — metadata; банк — приватное хранилище.
- Глобальная роль назначается администратором. Выбор «Ведущий — сразу активен» НЕ даёт самоэскалации; немедленное подтверждение только для заранее назначенного сервером LEAD/ADMIN. Bootstrap ADMIN — отдельная явная серверная операция по Telegram ID, не публичный login.
- 2.txt уточняет видимость состава: стажёр/ведущий видят свой отряд, а не все комнаты смены из 1.txt. Применяется более узкая privacy policy.
- Несколько отрядов одному пользователю допускаются (пример u6 в 3.txt). SquadMember — источник фактического состава. Привязка должности к отряду должна соответствовать членству, операции синхронизируются транзакционно.
- DailyMark: одна отметка на SquadMember + календарная дата (2.txt явно определяет это). Часовой пояс смены задаётся явно; SQL DATE не timestamp.
- PARTIAL требует непустого paymentNote; финансовую сумму без согласованной валюты не изобретаем.
- Import: одинаковое ФИО не является идентификатором. Preview показывает совпадения; обновление только по стабильному participant ID либо явному подтверждённому mapping. Автоматическое слияние из 2.txt отклоняется как небезопасное; default — не перезаписывать.
- Опрос: один атомарный SurveySubmission на user + survey. Необязательные вопросы не влияют на факт завершения. После первой отправки повторы запрещены.
- TechRequest владеет единственным programItemId, не дублируем FK в ProgramItem. Должность техлида — источник полномочий, назначение исполнителя только после назначения техлида и проверки должности исполнителя на этой смене.
- Неизвестная должность не даёт прав. Заместитель не назначает руководителя/не повышает глобальную роль. Scope проверяется прежде permission.
- Число завершённых смен считается по DISTINCT shiftId, не по числу должностей.

## ADR-004 — заявки и распределение персонала (этап 2)

- Сохраняем Foundation без переписывания: staffing routes регистрируются рядом с существующими routes; отдельный `StaffingService` отвечает за транзакционные сценарии, domain/staffing — за тип заявки и каталог должностей.
- Application APPROVED — допуск сотрудника на смену, ShiftRole — отдельная должность. Принятие не назначает права, снятие должности не удаляет допуск. ADMIN может добавить сотрудника вручную с созданием APPROVED Application, но не обходит существующую отклонённую заявку.
- Набор ведущих/стажёров управляется независимыми flags. Stage отображает этап и меняется ADMIN; не вводим неоговорённый автоматический запрет заявки по stage. Решения допускаются только PENDING→APPROVED/REJECTED; version-CAS предотвращает потерю решения из устаревшего UI. Пересмотр/withdrawal/reapplication требуют отдельной бизнес-политики и не включены.
- Каждая mutation перечитывает actor/shift внутри transaction и получает PostgreSQL row-lock Shift; это сериализует staffing mutations одной смены. Admission, audit и notification атомарны.
- shift.manage_roles даёт чтение минимального списка принятого персонала и управление назначениями данной смены; руководителя назначает/снимает только ADMIN. Должность с squadId требует существующего SquadMember с той же сменой и пользователем; Squad CRUD не включён.
- История построена на AuditLog, сохраняется после снятия роли. Пользователь видит собственные события; менеджер должностей не получает чужие application decisions; ADMIN видит полный staffing audit смены. Shared DTO не содержит Telegram ID/контакты/даты рождения.
- Результат рассмотрения и назначения сохраняется в Notification в той же transaction. Реализуется только in-app inbox, не обещаем отправку Telegram. Outbox worker остаётся последующим этапом.

## ADR-005 — этап 3: read-only метаданные отрядов (APPROVED, 2026-11-13)

Решения владельца продукта, не расширяющие текущий staffing:
- **D1 APPROVED:** только список и карточка метаданных `id/name/color/sortOrder`. Без количества, состава детей/сотрудников, CRUD, архивации, membership mutations, DailyMark, комнат, оплаты и заезда.
- **D2 APPROVED:** итоговый permission set вычисляется существующим resolver по должностям той же смены. `squad.view_all` разрешает все отряды доступной смены; иначе `squad.view_own` требует связь через `ShiftRole.squadId` или `SquadMember.userId` с совпадающими user/shift/squad. Источники объединяются, null squadId не даёт связи. Фильтр применяется в БД до пагинации и count разрешённых отрядов.
- **D3 APPROVED:** membership само по себе не даёт permissions. Без обоих view permissions новый list возвращает 403; detail не раскрывает объект (404). `squad.manage` не заменяет право просмотра.
- **D14 APPROVED:** active/auth по существующим соглашениям; невидимая смена, отсутствующий/чужой/недоступный отряд и неверная пара shift+squad — 404. Для list видимой смены отсутствие view permission — 403. List и detail используют общий object scope, не различают скрытые и отсутствующие target ID.
- **D12 APPROVED:** несколько членств сотрудника в разных отрядах одной смены допустимы. Это не расширяет permission set. Назначение должности не создаёт membership и наоборот; ShiftRole.squadId остаётся optional.
- Schema/миграции и ROLE_PERMISSIONS не изменяются. Существующий staffing metadata endpoint сохраняет минимальный список id/name для shift.manage_roles; он не становится API состава или новым Squad API.
- Отложены: lifecycle участника/членства, история переводов, обязательность фамилии ребёнка, архивация/удаление и все полевые права состава. Эти решения не блокируют метаданные и не считаются утверждёнными данным ADR.

## ADR-006 — дети и специализированный XLSX import (D15–D21 APPROVED)

Утверждённый backend-срез этапа 3, без объявления готовности UI:
- **D15/D18:** `SquadMember` типа CHILD — независимая запись конкретной смены. Нет глобальной сущности ребёнка, межсменных связей и поиска кандидатов вне shiftId.
- **D16/D17:** серверный XLSX parse/validate → preview → явное сопоставление → окончательный preview → explicit commit. Нормализованные полное имя + DOB служат только поиском кандидатов внутри смены, не уникальным ключом. Автоматическое объединение запрещено; неоднозначность требует выбора сотрудника.
- **D19:** существующей записи разрешено менять только squadId/building/room. ФИО/DOB, тип и userId неизменяемы в этом срезе. Import update требует одновременно participants.import и participants.edit_room; ручное размещение требует participants.edit_room. squad.manage не заменяет эти права.
- **D20:** no-op не создаёт участников и не выполняет UPDATE участника; повторный commit защищён состоянием ImportJob, параллельное создание — сериализацией на Shift и повторной проверкой кандидатов.
- **D21:** корректные строки допускаются при ошибках других строк; неразрешённые/ошибочные/конфликтующие строки сохраняются в результате с номерами и обезличенными причинами. Ни одна строка не теряется молча.
- Ручное создание — только CHILD, по squad.manage и в разрешённом отряде. Object scope сохраняет view_all/view_own; право действия не раскрывает чужой отряд. Педсостав, удаление участников/отрядов, архивирование, оплата, заезд и DailyMark исключены.
- XLSX: обязательны заголовки и значения «Фамилия», «Имя», «Дата рождения», «Отряд»; «Отчество», «Корпус», «Комната» необязательны. Даты — ДД.ММ.ГГГГ, ГГГГ-ММ-ДД или Excel-дата без угадывания двухзначного года. Неизвестный отряд — ошибка, без автосоздания; старые поля оплаты/заезда не применяются, с предупреждением.
- Переиспользуется ImportJob: preview с ПДн не более часа, серверная проверка срока и периодическая очистка. После commit — только номера строк, ID, статусы и обезличенные причины/счётчики; без ФИО, DOB и значений размещения. Исходный файл не сохраняется. Новый срок хранения обезличенного результата не вводится.
- ADR-005 остаётся историческим решением первого read-only среза; этот ADR расширяет только явно перечисленный backend scope. Frontend и весь этап 3 не объявляются завершёнными.

## Этапы и критерии приёмки
0. Аудит, baseline, полная карта функций (документы, без изменения TXT).
1. Воспроизводимый workspace, полная доменная схема с начальной миграцией, безопасный auth → onboarding → подтверждение → список/создание смен UI/API/DB; negative tests и сборки.
2. Заявки, назначение должностей, объектный RBAC, отряды/участники/дневные отметки; тесты изоляции и транзакций.
3. Банк/программа/история/предложения/техзапросы; реальные файлы и protected download.
4. Опросы/результаты/экспорт, документы/комментарии/knowledge; privacy и duplicate submission tests.
5. Preview/confirm CSV/XLSX/Google Sheets, bot webhook/commands и outbox worker с retry; интеграционные тесты.
6. Mobile e2e/визуальная проверка/CI/staging/backups/релизный security review.

## Инфраструктура и ограничения
Production: HTTPS reverse proxy раздаёт frontend и /api с одного origin, PostgreSQL, приватное S3-compatible storage, Telegram bot token/webhook secret. Локально Vite proxy /api. Никакие секреты не попадают в VITE_* или git. Docker/psql в текущем окружении отсутствуют: миграции и DB integration нельзя объявлять проверенными без реально доступной PostgreSQL.

## UX
Основная навигация: Главная / Смены / Банк / Опросы / Профиль; дополнительные Команда, База знаний, документы, уведомления через меню. Внутри смены: Этапы / Отряды / Программа / Техзапросы / Опросы. UI вводится по мере готовности API, не выдаёт отсутствие интеграции за успех. Mobile 320–430 px, Telegram theme/safe areas/back cleanup, labels/focus/44px touch targets, error/retry/empty/loading feedback и reduced motion.
